# pipe-io v0.6.0 - Dead-letter routing

**Date:** 2026-05-19
**Compare:** `v0.5.0...v0.6.0`

## Headline

Wires up `ErrorPolicy::DeadLetter`. The variant has been reserved
in the enum since `0.3.0`; this release lands the
`PipelineBuilder::dead_letter(sink)` method that turns it into a
real routing path. Closes the second of the three deferrals from
the `0.3.0` design lock. One deferral remains (the unified
`Driver` trait).

A stage running under `ErrorPolicy::DeadLetter` now emits
[`StageFailure`] records to the installed sink instead of
silently dropping. If no sink is installed, the policy still
behaves as `Continue` (documented no-sink fallback rather than
unreachable code).

The install handle is shared, so `.dead_letter(sink)` can be
called before or after the failing stages. Order does not matter.

## What changed since `v0.5.0`

### New - `PipelineBuilder::dead_letter`

```rust
impl<T, S, Acc> PipelineBuilder<T, S, Acc> {
    pub fn dead_letter<Sk>(self, sink: Sk) -> Self
    where
        Sk: Sink<Item = StageFailure> + Send + 'static;
}
```

`Sk` receives the `StageFailure` records produced by any stage
configured with `ErrorPolicy::DeadLetter`. The sink is invoked
in stream order with respect to the failures. After the main
pipeline finishes, the dead-letter sink receives `Flush` and
`Close`, so buffered or batching dead-letter sinks behave
correctly.

Available under `feature = "std"` (default-on); the no_std build
does not expose the method (an `Arc<Mutex>` handle is required
internally).

### Changed - `ErrorPolicy::DeadLetter` semantics

```text
prior (0.3.x - 0.5.x): silently equivalent to Continue
now (0.6.0+):          routes to the installed dead-letter sink;
                       degrades to Continue only when no sink is
                       installed (documented fallback).
```

The "no sink installed" path is intentional: it lets a builder be
configured optimistically with `.on_error(DeadLetter)` even when
the calling code hasn't decided where failures should go yet.

### Changed - Sink-error bubble-up

If the dead-letter sink itself errors, the failure surfaces from
`Pipeline::run` as
`Error::Sink { stage: StageId::new("dead_letter"), source: <boxed sink error> }`.
The original stage error that triggered the routing is lost in
this case; the assumption is that "your dead-letter sink is
broken" is the more actionable signal.

### New - `StageFailure::new` constructor

The locked `StageFailure` struct gains a public constructor:

```rust
impl StageFailure {
    pub fn new(stage: StageId, source: BoxError) -> Self;
}
```

The struct remains `#[non_exhaustive]`. Future releases may add an
`input` field to capture the failing record (would require
`Box<dyn Any + Send>` boxing at every failure site, deferred for
now).

### New - Tests

`tests/dead_letter.rs` adds 6 integration tests:

- `dead_letter_routes_failures` - parses a mixed-input stream;
  parseable items reach the main sink, failures land in the DLQ
  with the right `StageId`.
- `dead_letter_callable_before_failing_stage` - same scenario but
  with `.dead_letter()` called *before* the failing `try_map`,
  verifying install order does not matter.
- `dead_letter_without_sink_silently_drops` - omits the install
  call; failures drop silently.
- `dead_letter_sink_error_bubbles_up` - dead-letter sink that
  always errors; the run-level error names `"dead_letter"`.
- `fail_fast_overrides_dead_letter_install` - `FailFast` still
  short-circuits even with a DLQ installed.
- `continue_does_not_route_to_dead_letter` - `Continue` swallows
  errors without touching the DLQ.

## Semantics

```text
+---------------------------+
|         try_map           |
+-------------+-------------+
              |
              v
        Err(stage_err)
              |
+-------------+-------------+
|     ErrorPolicy::         |
|       FailFast            |---> Error::Stage { ... } bubbles from run
|       Continue            |---> drop, continue
|       DeadLetter          |
|         |                 |
|   DeadLetter handle?      |
|   - some(sink) -> route   |---> sink receives StageFailure
|   - none       -> drop    |---> same as Continue
+---------------------------+
```

The dead-letter handle is shared (`Arc<Mutex<Option<_>>>` under
std). Every stage that might fail under `DeadLetter` clones the
handle at build time; `.dead_letter(sink)` fills the slot at any
point before `run` is invoked.

## Migration

### From `v0.5.0`

No breaking changes. If you were configuring stages with
`.on_error(ErrorPolicy::DeadLetter)` in `v0.5.0` expecting it to
behave as `Continue`, that behaviour now becomes "route to
dead-letter sink if installed, otherwise drop". To preserve the
prior silent-drop behaviour, either:

- Leave `.dead_letter()` uninstalled (same observable outcome as
  `Continue`), or
- Switch the policy to `ErrorPolicy::Continue` explicitly.

To start collecting failures:

```rust
use pipe_io::{ErrorPolicy, Pipeline, StageFailure, sink::VecSink};

let dlq = VecSink::<StageFailure>::new();
let dlq_handle = dlq.handle();

Pipeline::from_iter(records)
    .stage_id("parse")
    .on_error(ErrorPolicy::DeadLetter)
    .try_map(|raw| parse(raw))
    .dead_letter(dlq)
    .sink(main_sink)
    .run()?;

for failure in dlq_handle.take() {
    log::warn!("dropped {}: {}", failure.stage, failure.source);
}
```

the `0.3.0` design lock remains:

surface in `REPS.md` but is not yet implemented; it will land
alongside the `Driver` trait or as a separate `0.7.x` slot.

## Acknowledgements

`pipe-io 0.6.0` closes the dead-letter slot. The shared-handle
design (`Arc<Mutex<Option<DeadLetterFn>>>`) made install-order
independence a free property and kept the change localized: the
existing `try_map` and `.stage()` closures route through a single
shared helper, and no stage type needed to learn about
dead-letter routing.

Next: `v0.7.0` - Driver trait + custom executors. That release
reconciles the `Send` bounds between `SyncDriver` and
`ThreadedDriver` and opens the door to a `pipe-io-tokio` adapter.
