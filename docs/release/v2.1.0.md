# pipe-io v2.1.0 - Bounded Windows by Default, Clock Steps Fixed

**Date:** 2026-11-12
**Compare:** `v2.0.0...v2.1.0`

## Headline

Windows now have finite memory limits out of the box, and a clock that
steps backwards can no longer make a sliding window emit the same
window twice. Both come from an independent review of `2.0.0`. No API
is removed or changed; one default changes, described below.

## Behaviour change: default window limits

`WindowSpec::max_items` and `WindowSpec::max_keys` used to default to
unbounded. A keyed window fed by untrusted keys (a client address, a
header value) kept one entry per distinct key for the whole window, so
memory grew with the number of keys an attacker could send.

Both now default to 1,048,576 (`window::DEFAULT_MAX_ITEMS` and
`window::DEFAULT_MAX_KEYS`):

- a window that reaches the item cap is emitted at once and a new
  window continues the same interval, as with an explicit `max_items`;
- when a new key arrives at the key cap, the least recently active key
  is flushed (its open windows are emitted early) and evicted, as with
  an explicit `max_keys`.

No item is dropped in either case. Pipelines that stay under a million
items per window and a million open keys see no difference. To keep the
old behaviour, set `max_items(usize::MAX)` and `max_keys(usize::MAX)`.
`WindowSpec::items_limit` and `keys_limit` still return `None` when no
limit was set.

## Fixed

- **Sliding windows and a clock that steps back.** The clock docs
  promise that an item stamped in the past joins the window that is
  currently open. Sliding windows instead created windows at the late
  item's own time, re-emitting windows that had already closed, ahead of
  the open ones. Every window stage now clamps the clock reading to the
  latest instant it has seen, for all three policies, keyed and
  unkeyed. Regression tests:
  `tests/review_2026_11.rs::sliding_window_backwards_clock_does_not_reemit_closed_windows`
  and the property test `non_monotonic_clock_never_emits_a_window_twice`.

## Documented

- **Cancellation latency.** Cancellation is graceful: under
  `run_threaded`, items already queued in `buffer` edges are still
  processed, and a source thread blocked on a full edge waits for room
  before it sees the flag. The `CancelHandle` docs and
  `docs/ARCHITECTURE.md` now state the bound: the items in flight (at
  most the sum of the `buffer` capacities, plus one per thread) times
  the per-item cost of the slowest stage.
- **Teardown needs unwinding.** Teardown on the panic path relies on
  unwinding. A binary built with `panic = "abort"` stops at the first
  panic and runs no teardown. README, `docs/ARCHITECTURE.md`, and a
  comment on the release profile say so.
- The ARCHITECTURE memory table and the README now give the default
  window limits.

## Compatibility

- MSRV unchanged (1.85). No runtime dependencies.
- Public API: additive only (`window::DEFAULT_MAX_ITEMS`,
  `window::DEFAULT_MAX_KEYS`).
- Output can differ from 2.0.0 only for windows above the new default
  caps, and for sliding windows fed by a clock that steps backwards.
